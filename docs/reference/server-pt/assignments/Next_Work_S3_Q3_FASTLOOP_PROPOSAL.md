## Q3 experiments and decisions

Keep the original M-DHCP identifiers and record each as measured, inconclusive, omitted or blocked with its reason. Do not flatten them into one success flag.

1. **Serving-pool behavior and subjects (M-DHCP-1/4/5).** Observe the server/interface/process, native default, intended pool, client identity/MAC, DHCP mode and initial address. Exercise the typed acquisition path under its pre-effect claim. Preserve request, response and post-read evidence. Success in configuration does not prove that a pool served a client.

2. **Lease-table calibration (M-DHCP-2).** Observe empty, one-row and full states using small explicitly selected fixtures. Preserve indexes, raw rows, return types, exceptions, repetitions and termination. Where a one-row/full case would be identical, use the minimal additional independent case necessary to discriminate it. Do not fabricate rows. A capacity limit is not a lease-count reader, and a transient getter failure is not automatically end-of-table.

3. **Acquisition versus attribution.** Distinguish native client addressing, a positive IP/MAC match in the intended pool, confirmed absence after a calibrated scan, and causal acquisition. Reuse canonical evidence rules. A matching row can support presence without proving universal exclusivity or DORA internals. A wrong-MAC row is a contradiction. An absent row is a contradiction only when the observation contract can establish absence; otherwise retain incompleteness.

4. **Capacity-one negative.** A second client on a one-user intended pool supports `lease_not_acquired` only with the required completed negative observations. If it receives an address from the native default, preserve that as a distinct observed result, not as intended-pool success or exhaustion. Do not modify the default to rescue the control.

5. **Time and renewal (M-DHCP-6).** Keep two timed readings without a newly requested acquisition, followed by an automatic-renewal observation and, only under an explicit typed contract, a requested-renewal experiment. A string change is not proof of renewal. No explicit request is not proof of absent background traffic. If natural renewal does not occur within the declared observation horizon, preserve INCONCLUSIVE; do not change the simulation clock or lease settings to force it.

6. **Claim repeat and events.** The same-action repeat must demonstrate that no second `dhcpRun` is sent. Requested renewal is a different operation from replay and cannot be smuggled through by deleting a claim or changing a nonce. If no safe typed renewal contract exists, name that measurement gap explicitly. M-DHCP-3 remains under the approved event deferral; this order does not qualify callbacks, zero-event unregister, `dhcpRelease` or `resetDhcpConfOn`.

The R-EVT-05 fallback remains active. Read-back plus table attribution must not silently become `DHCP_LEASE=VERIFIED`. Any new decision predicate needs a design delta and causal controls before use.
