### 3. DHCP design decisions belong to you

A separately named intended pool is not an end-user requirement unless the supplied intent explicitly makes it one. An effective implementation may manage the native pool, prevent an overlapping pool from serving, or use another evidenced arrangement that preserves Server-PT as the requested authority. Choose the least complex sustainable design supported by observations. Do not silently substitute router DHCP or change the requested network to match an accidental lease.

Cisco's server help says the default `serverPool` cannot be modified or edited, while the generic Extensions API documents pool setters and process pool-removal operations. This does not establish that those operations work on the native pool in build 9.0.1.0858. You may investigate that discrepancy with documented APIs on an owned disposable server. Treat unsupported/no-op setters, regeneration, exceptions and unexpected side effects as observations, not success. No binary patching, memory manipulation or hidden API guesses.

Before adopting a strategy, distinguish the logical requested pool from its effective backend object. Read back the requested range, mask, exclusions, gateway, DNS and relevant capacity; preserve physical pool identity and lifecycle. Characterize overlapping pools and restart/reapplication behavior. Adopting `serverPool` is permissible only if it actually realizes the intent; renaming a contradictory result in the report is not.

Acquisition state and action causality are separate contracts. Autonomous acquisition after legitimate DHCP activation is not inherently a product failure. You may implement a state-based usable-lease prerequisite without claiming that a later `dhcpRun` caused it. It must establish coherent fresh client configuration, acceptable allocation and exclusions, stable binding to the selected interface/MAC, and defensible effective-server/pool attribution. An out-of-policy address remains a contradiction. A changed lease string is not proof of renewal.

A positive matching lease does not require proving absence elsewhere. Do not block basic usability solely on unneeded end-of-table or renewal knowledge. Conversely, exhaustion, absence and renewal claims require their own evidence. A repeated `invalid vector subscript` may be studied as a build-scoped candidate terminator using known occupancy and negative controls; an arbitrary exception must never become a generic end-of-table rule.

Controlled acquisition/release/reset experiments on owned disposable clients are allowed when their real API contract is verified and the action is recorded as a distinct intervention. Never reset a claim or resend an uncertain mutation to obtain a clean story. R-EVT-05 remains in force until any required event source, delivery, identity and release behavior are qualified. Prefer existing read-based routes when sufficient.
